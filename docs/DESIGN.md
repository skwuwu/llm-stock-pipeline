## 0. 설계 원칙 (모든 결정의 기준)

1. **PIT-first**: 모든 사실(fact)은 `(as_of, reported_at, value)` 3중 키로 저장한다. 룩어헤드는 버그가 아니라 데이터 모델로 차단한다.
2. **Raw는 불변**: API 응답 원문을 그대로 보존하고, 정규화는 항상 raw에서 재생성 가능해야 한다(재파싱 가능성 = 버그 수정 가능성).
3. **LLM은 추출기이지 판단기가 아니다**: LLM 출력은 반드시 원문 근거를 동반하며, 근거가 검증되지 않으면 폐기한다.
4. **모든 단계는 멱등(idempotent)**: 같은 `run_date`로 재실행 시 동일 결과. LLM은 캐시 키로 멱등성 확보.
5. **오탐 비용 > 누락 비용**: 애매하면 통과시키지 않고 플래그를 단다. 스크린은 아이디어 생성기이지 매수 신호가 아니다.

## 1. 아키텍처 개요

```
                 ┌──────────────── raw/ (immutable, parquet+json) ────────────────┐
DART OpenAPI ───▶│ dart/list, dart/fnltt, dart/stocktotqy, dart/document          │
KRX/pykrx    ───▶│ krx/ohlcv, krx/cap, krx/sector                                 │
EDINET v2    ───▶│ edinet/docs, edinet/xbrl                                       │
J-Quants     ───▶│ jpx/ohlcv, jpx/shares                                          │
                 └───────────────────────────┬───────────────────────────────────┘
                                             ▼
                        [L1] normalize  →  normalized/facts_financial.parquet
                                           normalized/prices.parquet
                                           normalized/security_master.parquet
                                             ▼
                        [L2] derive     →  derived/metrics.parquet  (PER/PBR/FCF/…)
                                           derived/quality_flags.parquet
                                             ▼
                        [L3] screen     →  screens/{run_date}/survivors.parquet
                                             ▼
                        [L4] enrich     →  enrich/{corp}/business.md, segments.json
                                             ▼
                        [L5] llm-tag    →  llm/tags/{cache_key}.json   (per-stock)
                        [L6] llm-cluster→  llm/themes/{run_date}.json  (reduce)
                                             ▼
                        [L7] verify     →  verify/{run_date}/verdicts.parquet
                                             ▼
                        [L8] report     →  out/{run_date}/digest.md | digest.html
                        [L9] loopback   →  backtest adapter (외부 백테스터)
```

**스토리지**: DuckDB + Parquet. Postgres는 초기에 불필요.
DuckDB 하나로 PIT `ASOF JOIN`이 native 지원되므로 시점 결합이 SQL 한 줄로 끝난다.

```sql
-- 룩어헤드 없는 재무 결합의 정석
SELECT p.*, f.net_income, f.equity_controlling
FROM prices p
ASOF LEFT JOIN facts_financial f
  ON f.ticker = p.ticker AND f.available_at <= p.date
```

**오케스트레이션**: 초기엔 Typer CLI + 단계별 커맨드(`pipe ingest`, `pipe screen`, …).
각 커맨드는 `--run-date`, `--market` 인자를 받고 산출물 경로로 완료를 판정한다.
Prefect/Dagster는 스케줄이 필요해질 때 도입(그 전엔 오버엔지니어링).

>
> KIND 업종은 KSIC 소분류(159종)라 KRX 대분류보다 세밀하다 — "전동기·발전기 및 전기
> 변환·공급·제어 장치 제조업"이 독립 항목이라 AI 전력기기 테마 판별에 오히려 유리하다.
> `configs/sectors/kind_industry_map.yaml` 이 159종 → 내부 35코드로 매핑한다(커버리지 100%,
> `tests/test_m1_sector_status.py` 가 회귀 방지).

- **API 한도**: DART 20,000 콜/일. 전종목 x 전분기 백필은 반드시 배치 분할 + 로컬 캐시.
- **`reprt_code`**: `11011` 사업, `11012` 반기, `11013` 1Q, `11014` 3Q.
- **`fs_div`**: `CFS`(연결) 우선, 없으면 `OFS`(별도). **어느 쪽을 썼는지 반드시 컬럼으로 남긴다.**

### 2.2 JP

| 데이터 | 소스 | 비고 |
|---|---|---|
| 제출서류 목록 | EDINET API v2 `documents.json?date=&type=2` | **Subscription-Key 헤더 필수** (v2부터) |
| XBRL 본체 | EDINET `documents/{docID}?type=1`(zip) / `type=5`(CSV) | CSV가 파싱 훨씬 쉬움 — 여기서 시작 |
| 시세·주식수 | J-Quants API (무료 티어는 12주 지연) 또는 유가증권보고서 값 | 지연 티어는 백테스트엔 OK, 실시간 스크린엔 부적합 |

**JP 특유의 함정**:
- 회계기준 3종 혼재 → 택소노미 prefix가 다르다. `jppfs_cor:`(JP-GAAP), `jpigp_cor:`(IFRS), US-GAAP 제출사 별도.
  정규화 레이어에서 **기준별 요소명 매핑 테이블**을 두고, 미매핑은 조용히 0이 아니라 `NULL + unmapped_element` 플래그.
- 2024년 제도 변경으로 **四半期報告書 폐지 → 半期報告書**. 1Q/3Q 재무는 EDINET에 없고 TDnet 決算短信에 있다.
  → JP는 **반기 주기 파이프라인**으로 설계하고, 분기 데이터는 optional 확장으로 둔다.
- 결산월이 3월에 대량 집중. as-of 정렬 시 3월 결산 쏠림을 감안(리밸런싱 시점 설계에 영향).

### 2.3 PIT 저장 규약

모든 재무 fact 행:

```
ticker, market, corp_id,
fiscal_year, fiscal_quarter, fiscal_end_date,   -- 이 숫자가 "언제의" 사실인가
reported_at,                                    -- 공시 접수일 (DART rcept_dt / EDINET submitDateTime)
available_at,                                   -- reported_at + lag(기본 0영업일, 설정 가능)
statement_basis,                                -- CFS | OFS | IFRS | JGAAP
element, value, unit,
source_doc_id, source_url, ingested_at,
revision_of                                     -- 정정보고서면 원본 doc_id
```

- **정정공시**: 기존 행을 UPDATE하지 않는다. 새 행을 `revision_of`와 함께 append.
  → "그때 우리가 알던 값"과 "지금 확정된 값"을 둘 다 질의 가능. 백테스트 정직성의 핵심.
- `available_at` 기본 lag = 0일이지만, 장중 공시/장마감 후 공시 구분이 필요하면 `+1영업일`을 기본값으로 두는 게 안전하다.

## 3. L1/L2 — 정규화 & 파생지표

### 3.1 정규화 산출물

- `security_master`: ticker, name, market(KOSPI/KOSDAQ/TSE-Prime/…), sector_code, listing_date, delisting_date, is_preferred, is_spac, is_reit, is_holding, is_financial
- `prices`: date, ticker, close, adj_close, shares_outstanding, treasury_shares, market_cap
- `facts_financial`: 위 PIT 스키마

### 3.2 파생지표 — 계산 규약 (여기가 오탐의 90%)

| 지표 | 정의 | 주의 |
|---|---|---|
| `per` | `market_cap_common / net_income_controlling_ttm` | **우선주 시총 별도 처리** |
| `pbr` | `market_cap / equity_controlling` | 분모는 지배주주지분 — 총자본 쓰면 과소평가 |
| `per_op` | `EV / 영업이익` 또는 `시총 / (영업이익×(1−t))` | **일회성 이익 왜곡 교차검증용** |
| `per_5y` | 시총 / 5년 평균 순이익 | Graham/CAPE식. 경기민감주 방어 |
| `fcf` | 영업활동현금흐름 − CAPEX | 금융업은 계산하지 않음(NULL) |
| `net_cash` | 현금성자산 − 총차입금 | 넷캐시 > 시총 케이스 별도 하이라이트 |

> `bps`·`eps_ttm` 은 v1 에 정의돼 있었으나 **소비처가 없어 2026-08-07 제거**했다.
> PBR·PER 이 같은 정보를 주가 대비로 담고 있다. 필요해지면 2줄이면 되살린다.

#### 고아 지표를 만들지 않는다

계산 비용을 쓰고 아무도 안 읽는 지표는 단순한 낭비가 아니다 — `payout_ratio` 는
고아인 채로 `_safe_div` 스칼라 버그를 안고 있었고, **아무도 읽지 않아 아무도 몰랐다.**

`test_no_orphan_derived_metrics` 가 파생 수치지표 전건을 훑어, 셋 중 어디에도
해당하지 않으면 실패시킨다:
(a) 설정이 `metric`·`expr` 로 참조 · (b) 다른 모듈이 참조 · (c) metrics.py 안에서
다른 지표를 만드는 데 쓰임. `CRITICAL_METRICS` 등재는 (c)로 세지 않는다 —
무결성 가드에 이름이 있다는 이유로 고아가 '사용 중'으로 위장되면 검사가 무의미해진다.

2026-08-07 전수 조사에서 5개를 정리했다: `bps`·`eps_ttm`(소비처 없음),
`div_yield_gap`(체크가 `expr` 로 직접 계산하게 되며 대체), `largest_holder_pct`·
`largest_holder_pct_raw`(`owner_stake` 로 대체). 파생 수치지표 56 → 51개.

`LARGEST_HOLDER_PCT` **fact 는 스토어에 남긴다** — 이미 수집했고(2,756콜),
raw 성격의 사실이라 지울 이유가 없다. 지운 것은 그 위에 얹었던 파생 컬럼뿐이다.

**우선주 처리(KR)**: `005930`(보통주)과 `005935`(우선주)는 별도 티커.
PER 계산 시 분자는 **보통주 시총 + 우선주 시총**, 스크린 대상은 보통주 티커 하나로 dedup.

### 3.3 품질 가드 (`quality_flags`) — "쓰레기 PER이 통과하지 않게"

각 종목-일자에 대해 boolean 플래그 집합을 만들고, 스크린은 **하드 배제**와 **소프트 플래그**를 구분한다.

**하드 배제 (스크린 진입 불가)**
- `equity_controlling <= 0` (자본잠식) — PBR이 음수가 되어 `PBR < 1`을 그냥 통과함. **반드시 `0 < PBR < 1`로 작성.**
- `net_income_ttm <= 0` — 마찬가지로 `0 < PER < 10` 형태로 하한을 명시.
- 관리종목 / 거래정지 / 감사의견 비적정 / 상장폐지 실질심사
- SPAC, 리츠, ETF/ETN, 우선주(중복), 스팩합병 직후
- 최근 재무 공시 경과일 > 200일 (좀비 데이터)
- 결산기 변경으로 회계기간 ≠ 12개월인 TTM

**소프트 플래그 (통과시키되 다이제스트에 표기, LLM에도 전달)**
- `oneoff_profit_suspect`: `net_income_ttm > operating_income_ttm × 1.5` → 영업외/일회성 의심
- `per_op_divergence`: `per_op / per > 3` → 본업 대비 이익 과대
- `financial_sector`: 은행/보험/증권 — FCF·PBR 해석 규칙이 다름
- `holding_company`: 지주사 — 순자산가치 할인 이슈
- `micro_liquidity`: 20일 평균 거래대금 < 임계 (시총 필터와 별개)
- `earnings_volatility_high`: 5년 순이익 표준편차/평균 > 1
- `cfs_missing_used_ofs`: 연결 없어 별도 사용
- `unmapped_elements > 0`: XBRL 요소 미매핑 존재 (JP에서 자주)

#### 무료 가격 소스는 서로 독립이 아니다 (2026-08-07 실측)

두 번째 가격 소스를 붙이려 후보를 검증했다.

| 후보 | 결과 |
|---|---|
| **pykrx** | ❌ import 시점에 `KRX_ID`/`KRX_PW` 를 요구한다. KRX 데이터포털 계정이 필요해 KIS 와 같은 종류의 마찰이다 |
| **yfinance** | ⚠️ 작동하지만 **FDR 과 동일 데이터** — 종가·거래량이 모든 날짜에서 원 단위까지 일치 |
| **FDR** | 현재 운영 소스 |

```
포스코스틸리온        FDR종가    yf종가   FDR거래량    yf거래량
2026-08-03           4,265     4,265     173,046     173,046
2026-08-06           4,615     4,615     128,562     128,562
```

**교차검증 가치가 0 이다** — 틀린 값까지 똑같이 재현한다. 폴백으로는 쓸 수 있다.

결론: **무료 독립 가격 소스는 없다.** KIS 를 쓰지 않기로 하면 주가끼리 대조하는
길은 막힌다. 그래서 아래 두 가드로 대신한다 — 둘 다 **DART 에서 오는 값**과
대조하므로 주가와 완전히 독립이다.

| 자산주 | 낮음 | 정상 | 정상 — PBR 만 낮다 |
| **포스코스틸리온** | **0.072** | **0.0246** | **둘 다 무너짐 → 시총이 틀렸다** |

`PBR < 0.15 AND PSR < 0.08` 로 6건을 잡는다. 시총이 자본의 **3~13%** 인 조합인데,
그런 상장사는 없다(포스코스틸리온 시총 277억 / 자본 3,841억 / 매출 1조 1,275억).
금융업은 '매출' 개념이 달라 제외한다.

`MIN_PLAUSIBLE_PBR` 도 **0.001 → 0.02** 로 조였다. 기존 값은 50배 느슨해 시총이
자본의 2% 인 종목도 그냥 통과시켰다. 0.05(분포 p0.1%)까지 올리지 않은 이유는
자산주가 극단적으로 싸질 여지를 남기기 위해서다 — '불가능' 구간만 막는다.

##### 두 가드는 상보적이다

| | 배제 | 커버리지 |
|---|---|---|
| `price_dividend_inconsistent` | 11 | DPS>0 인 46% 만 |
| `market_cap_inconsistent` | 6 | 유니버스 100% |
| 중복 | 3 | |

6건 중 **3건은 배당 가드가 못 잡는다.** 테스트가 이 상보성을 강제한다
(한쪽이 다른 쪽의 부분집합이 되면 실패).

#### 가격 소스 교차검증 ✅ 2026-08-07

단일 소스로는 주가 오류를 잡을 수 없다. **시총·PER·PBR 이 전부 같은 종가에서
나오므로** 종가가 틀리면 셋이 함께 틀리고 서로를 검증하지 못한다.

`src/pipeline/ingest/price_sources.py` 가 소스 무관한 계약(`ticker, close,
adtv_20d, price_date`)과 대조 로직을 담는다.

```
pipeline ingest-prices --as-of <date> --source fdr --cross-check kis
  → 종가 대조 → price_source_disagree 플래그 → 하드가드
```

**불일치해도 값을 지우지 않는다.** primary 값을 그대로 두고 플래그를 달고
반대편 값을 `price_alt_close` 에 남긴다 — 어느 쪽이 맞는지 모르는 상태에서
임의로 하나를 고르면 틀린 값을 확신을 갖고 쓰게 된다. 판정은 하드가드가 한다.

소스가 하나면 플래그는 전부 False 인데, 그건 **'이상 없음'이 아니라
'검증하지 못했음'**이다. 매니페스트에 `compared: 0` 으로 구별하고 실행 시 경고한다.

##### 미검증 소스 게이트

KIS 어댑터(`ingest/kis.py`)는 작성 시점에 자격증명이 없어 **엔드포인트·필드명을
실제 응답으로 확인하지 못했다.** 추측한 배선으로 2,598종목을 돌리다 실패하면
실패를 알아채는 시점이 레이트 리밋을 소진한 뒤가 된다.

그래서 프로브를 통과하기 전에는 대량 수집이 **거부된다**:

```
pipeline probe-price --source kis --as-of <date>   # 4종목으로 확인
```

검증 상태는 마커 파일로 남긴다 — 프로브와 수집이 다른 프로세스라 메모리
플래그만으로는 게이트가 성립하지 않는다. 프로브 자신은 게이트를 통과시킨다
(게이트의 목적은 대량 수집을 막는 것이지 검증을 막는 것이 아니다).

인증 실패는 종목별 `except` 로 삼키지 않는다 — 그러면 '자격증명 없음'이
'종가를 하나도 못 받음'으로 둔갑해 원인이 감춰진다.

#### 배당 역산 주가 교차검증 ✅ 2026-08-07

시총·PBR 은 전부 **같은 종가**에서 나오므로 종가가 틀리면 셋이 함께 틀린다.
서로를 검증하지 못한다. 배당은 종가와 **독립된 소스**라 유일한 교차검증 수단이다.

```
역산 주가 = 주당배당금 ÷ 회사가 보고한 배당수익률
```

실측: 대한제분 DPS 4,000원 ÷ 3.0% = **153,846원**인데 저장된 종가는 **11,510원**.
배당 역산 *주식수*(배당총액÷DPS)는 정확했으므로(배율 0.98) 틀린 쪽은 종가다.
**종가 과소 → 시총 과소 → PER·PBR 이 인위적으로 싸 보인다** — 스크린이 가장
속기 쉬운 방향이다(포스코스틸리온 PBR 0.072, 미원화학 0.129).

검증 가능 1,191종목(보고 수익률 ≥ 0.1%. 그 미만은 분모가 작아 역산이 폭주한다 —
영풍 DPS 5원/0.01%). 5배 이상 괴리 16건.

**어느 쪽이 틀렸는지 갈라낸다.** 이걸 안 하면 DART 입력 오류 때문에 멀쩡한 종목이
배제된다:

| 판정 | 조건 | 건수 | 처리 |
|---|---|---|---|
| 배당 데이터 오류 | 보고 수익률 > 20% 또는 DPS > 주가 | 5 | **배제 안 함** — 주가를 의심할 근거가 아니다 |
| 판별 불가 | 그 외 5배 이상 괴리 | 11 | **하드가드 배제** |

배당 오류 실측: 아비코전자 수익률 30%·DPS 30원(DART 가 같은 값을 두 칸에),
와이엔텍 DPS **18억원/주**(배당총액을 주당란에 기입).

'판별 불가'를 배제하는 이유는 이 지점에서 **주가 오류와 실제 급락을 구별할 수단이
없기 때문**이다. 모르는 것을 통과시키지 않는다 — 시총 결측을 배제하는 것과 같은 판단이다.

> 현재 62종목은 이 가드 이전에도 오염되지 않았다. 다만 **설계가 막은 게 아니다** —
> 주가가 1/9 이라 시총도 1/9 이 되어 시총 하한(500억)에 걸린 덕이다. 오차가 3배였다면
> 하한을 넘어 "PBR 0.3 짜리 대박"으로 통과했을 것이다.

#### 랭킹 음수 가드 ✅ 2026-08-07

`composite_z` 는 가중치 부호로 방향을 표현하는데(per −0.40 = 낮을수록 좋음),
음수 값에 대한 가드가 없었다:

```
composite_z(PER −2 / 5 / 50) = [0.341, 0.220, −0.561]   ← 음수가 1등
```

적자면 PER 이 음수가 되므로 **적자 종목이 랭킹 최상위를 차지한다.** 지금은
`negative_earnings` 하드가드가 먼저 걸러 무해하지만, 가드를 손대는 순간 터진다.
가중치가 음수인 지표는 값이 0 이하면 '모름'으로 두고 최악으로 채운다.
`fcf_yield` 처럼 가중치가 양수인 지표는 음수가 정상적인 의미를 가지므로 건드리지 않는다.

**핵심 KPI**: `data_defect_rate` = 스크린 통과 후 수동/자동 검수에서 데이터 오류로 판정된 비율.
이걸 릴리스마다 기록한다. 이 파이프라인이 "정상 동작"의 정의.

## 4. L3 — 스크리닝

설정은 코드가 아니라 YAML로. 실제 설정은 `configs/screen/kr_deep_value.yaml`,
구현은 `src/pipeline/screen/gate.py`.

**하드 가드는 절대 튜닝하지 않는다.** 자본잠식·거래정지 종목이 목표 개수를 맞추려다
통과하면 파이프라인의 존재 이유가 사라진다. 튜닝 대상은 정량 필터뿐이다.

### 체크 — 설정으로 켜고 끄는 스크린 조건 ✅ (2026-08-07)

한 체크 = 설정 한 블록. `enabled` 로 on/off, `threshold` 로 절대 수치를 바꾼다.
구현은 `src/pipeline/screen/checks.py`.

```yaml
- id: high_leverage
  enabled: true
  kind: soft_flag            # hard_guard | gate_filter | soft_flag
  metric: debt_ratio
  op: ">"
  threshold: 2.00            # ← 코드가 아니라 여기서 바꾼다
  exclude_sectors: [BANK, INSURANCE, SECURITIES, OTHER_FIN, REAL_ESTATE]
  note: 부채비율 200% 초과
```

| kind | 역할 | 튜닝 |
|---|---|---|
| `hard_guard` | 절대 배제 | ❌ |
| `gate_filter` | `t` 로 loose↔tight 보간, 종목 수 조절에 참여 | ✅ |
| `soft_flag` | 통과시키되 다이제스트에 표기 | — |

`kind` 를 바꾸는 것만으로 역할이 옮겨간다. 코드 수정이 필요 없다.

**현재 켜진 체크 9개** — 전부 `soft_flag` 다. 배당 2개를 뺀 7개는 신규 API 호출 0회로 만들어졌다:

| id | 지표 | 임계 | 62종목 중 |
|---|---|---|---|
| `low_roic` | NOPAT / (자본+순차입금) | < 0.05 | 15 |
| `low_current_ratio` | 유동자산 / 유동부채 | < 1.00 | 13 |
| `treasury_heavy` | 자기주식 / 발행주식총수 | > 0.05 | 11 |
| `high_leverage` | (자산−자본) / 자본 | > 2.00 | 6 |
| `low_roe` | 지배주주순이익 / 지배주주지분 | < 0.05 | 3 |
| `cfo_shortfall` | 영업현금흐름 / 순이익 | < 0.50 | 2 |
| `accrual_anomaly` | (순이익−영업현금흐름) / 총자산 | > 0.10 | 0 |
| `payout_excessive` | 배당성향(DART 보고값) | > 0.80 | 0 |

**켜면 조용히 통과하는 게 아니라 실행이 실패한다** — `requires_source` 는
설정에 적기만 하면 통과하는 게 아니라 스토어에 실제로 적재됐는지 확인한다.

#### 지배구조 (DART hyslrSttus) ✅ 2026-08-07

2,756콜, 실패 0, 데이터 없음 224. 지표는 개인 최대주주가 아니라
**최대주주 및 특수관계인 합계**(`owner_stake`)다 — 개인 지분만 보면 가족·계열사로
분산 보유한 회사가 취약해 보인다(실측: 화천기공 본인 17.93% / 합계 48.78%).

#### L2 데이터 무결성 가드 ✅ 2026-08-07

`_safe_div(a, 100.0)` 에서 스칼라 분모가 **1행짜리 Series** 로 만들어져 인덱스
정렬로 첫 행만 계산되고 `payout_ratio` 가 통째로 NaN 이었다. 그때 테스트는
196개가 전부 통과하고 있었다 — **예외를 던지지 않는 고장은 테스트 수로 잡히지 않는다.
산출물 자체를 검사해야 한다.**

`assert_metrics_sane()` 이 `derive` 마지막에 돈다:
- 핵심 지표 15개 중 하나라도 **전부 NaN** 이면 `MetricsIntegrityError`
- 컬럼이 아예 없어도 실패
- 컬럼별 결측률을 `quality_{date}.json` 의 `nan_rate` 에 기록해 추이를 본다

근본 원인인 `_safe_div` 도 고쳤다(스칼라 브로드캐스트 + 인덱스 불일치 시 reindex).

#### 인증키 형식 검증 ✅ 2026-08-07

`.env` 의 DART 키가 **37자로 잘려** 있었는데, 증상은 "등록되지 않은 인증키" 라는
원인 불명 에러뿐이었다. `validate_dart_key()` 가 클라이언트 생성 시 형식(40자리
16진수)을 검사한다. **예외 메시지에 키 값을 넣지 않는다** — 길이와 16진수 여부만
알려준다(로그·스택트레이스로 새어나가면 안 된다).

#### 배당 (DART alotMatter) ✅ 2026-08-07

전 유니버스 2,759종목, **2,754 API 콜, 실패 0**. 커버리지 97%(2,531/2,598),
스크린 62종목은 **결측 0**.

별도 테이블을 만들지 않고 `facts_financial` 에 element 로 넣는다
(`DPS_CASH`, `PAYOUT_RATIO_PCT`, `DIV_YIELD_REPORTED_PCT`, `DIVIDEND_TOTAL_MM`).
그래야 `available_at` / `revision_of` / `renormalize` 기계장치를 그대로 쓴다.

**PIT 규율이 특히 중요한 데이터다.** 배당은 결산일이 아니라 정기주총 뒤
사업보고서로 확정 공시된다. `reported_at` 을 결산일(2025-12-31)로 두면 실제로는
이듬해 3월에야 알 수 있었던 것을 미리 아는 **3개월치 룩어헤드**가 된다.
그래서 `rcept_no` 앞 8자리를 접수일로 쓴다(실측: 화천기공 2026-03-18).

배당수익률은 회사가 보고한 값이 아니라 **as_of 종가로 다시 계산**한다.
회사 보고값은 결산 무렵 기준가 기준이라 스크린 시점의 수익률이 아니다.
보고값과의 괴리는 **원인을 나눠야** 쓸모가 있다. 하나로 뭉치면 '주가가 움직였다'
(정상)와 '수치가 안 맞는다'(오류)가 구별되지 않는다. 세 갈래로 나눴다:

| 지표 | 뜻 | 유배당 1,205 중 |
|---|---|---|
| `div_yield_gap` | 보고 시점 대비 수익률 상승 = **그 사이 주가 하락** | 71 |
| `dividend_total_gap` | DPS×주식수 vs 보고 배당총액 불일치 = **DART 자체 오류** | 35 |
| `dividend_fcf_cover` | FCF / 배당총액 — 1 미만이면 현금·차입으로 메우는 중 | 449 |

**과거 배당은 미래 배당을 보장하지 않는다.** 실적이 꺾인 저PER 고배당은
배당 트랩일 확률이 높고, 그 신호가 바로 `div_yield_gap` 이 크면서
`dividend_fcf_cover < 1` 인 조합이다(실측: 엠앤씨솔루션 보고 1.82% → 현재 15.4%,
FCF 커버 −0.60).

`dividend_total_gap` 은 기업 특성이 아니라 **데이터 품질 플래그**다. 화천기공은
배당성향(25.13%)·순이익·DPS 가 서로 정합적인데 `현금배당금총액` 만 1.51배로
어긋난다 — DART 가 내보내는 값끼리 안 맞는 경우다. 그래서 배당총액은 신뢰하지 않고
**DPS 로 역산한 값**을 쓴다.

**미수집과 무배당을 구분한다.** 응답이 있는데 값이 `-` 면 무배당(0)이고,
응답 자체가 없으면 모름(NaN)이다. 이 구분이 없으면 미수집 종목이 무배당으로
둔갑해 배당 스크린에서 조용히 탈락한다.

##### 게이트 커버리지 가드

`higher_better` 게이트에서 NaN 은 마스크가 False 가 되어 **그대로 탈락한다.**
수집이 덜 된 채 게이트를 켜면 '데이터를 못 받은 종목' 과 '조건 미달' 이
구별되지 않고 사라진다. `max_missing`(기본 5%)을 넘으면 실행을 거부한다 —
감수하려면 설정으로 올려 **명시적으로** 감수한다.

##### 게이트 승격을 하지 않은 이유 (시뮬레이션)

`dividend_yield_min` 을 `gate_filter` 로 켜면:

```
62종목 → 65종목 (t 0.709 → 0.547)
  빠짐 16 / 들어옴 19  ← 바스켓의 절반 이상 교체
  임계값: per 8.62→10.08, pbr 0.74→0.84
```

**종목 수는 안 줄고 밸류 기준이 오히려 느슨해진다.** 이분탐색이 배당 조건을
넣을 자리를 만들려고 `t` 를 낮추기 때문이다. 신규 19종목은 골든셋 라벨이 없어
오분류율 측정도 끊긴다. 그래서 관찰용 `soft_flag` 로 먼저 켜 두었다.

승격하려면: `pipeline screen --as-of <date> --enable dividend_yield_min`
(설정 파일을 바꾸지 않고 한 번만 시험할 수 있다.)

#### 왜 전부 soft_flag 로 시작하는가

`hard_guard`/`gate_filter` 로 켜면 생존 종목이 바뀌고, 그러면 **골든셋이 무효화된다**
— 라벨은 티커 단위라 새로 들어온 종목에 라벨이 없다. soft_flag 는 생존 종목을
건드리지 않으므로(실측: 62종목 전건 동일) 오분류율 측정을 유지한 채 분포를 먼저 본다.

승격 판단은 `pipeline screen --preview` 로 한다. 임계값을 감으로 정하지 않기 위해
**두 모집단**의 적중 수와 분위수를 함께 보여준다 — 전체 유니버스에는 적자·자본잠식
종목이 그대로 있어 분포가 왜곡되기 때문이다.

```
id                     kind             전체       가드통과   계산불가  가드통과 분포(p10/p50/p90)
low_roic               soft_flag  1478 ( 57%)   379 ( 33%)      78  0.0101 / 0.0715 / 0.215
high_leverage          soft_flag   275 ( 11%)    78 (  7%)      16  0.15 / 0.608 / 2.02
```

가드 통과 집합의 **33% 가 ROIC < 5%** 다. 자본비용에 못 미치는 밸류 트랩이 딥밸류
후보의 3분의 1이라는 뜻으로, 임계값 오설정이 아니라 그 자체가 신호다.

#### 가드 효과 리포팅 (2026-08-07)

**가드가 '돌고 있다'와 '무언가를 막고 있다'는 다르다.** 컬럼이 있어 `MissingGuardError`
는 안 나지만 유니버스 구성 때문에 한 건도 배제하지 않는 가드가 생길 수 있다.
그 상태는 조용해서 위험하다 — 지켜주고 있다고 믿는데 실은 아무것도 안 막는다.

`guard_effectiveness()` 가 가드별 배제 건수를 세고, 0건이면 실행 시 경고하며
매니페스트 `guards.inert` 에 남긴다. 현재 무력 가드 2건:

| 가드 | 배제 | 왜 0건인가 | 왜 빼지 않는가 |
|---|---|---|---|
| `is_spac` | 0 | `ingest-dart` 가 이미 걸러 facts 가 없다 | 수집 경로가 바뀌면 마지막 방어선 |
| `is_preferred` | 0 | KIND 목록이 **법인 단위**라 우선주 종목이 유니버스에 없다 | 종목 단위 소스로 바꾸면 즉시 필요 |

> 처음에는 이 둘을 `pending_guards` 로 옮기려 했는데, 그러면 **강제되지 않는다.**
> 소스가 바뀌었을 때 조용히 뚫린다. 위치를 옮기는 게 아니라 **0건이라는 사실을
> 보이게** 만드는 것이 맞다.

#### 규율

1. **켜져 있는데 데이터가 없으면 실패한다** (`CheckDataError`). `MissingGuardError`
   와 같은 규율 — 가드가 도는 줄 알고 안 도는 상태가 가장 위험하다.
2. **꺼진 것도 매니페스트에 기록한다.** 결과만 보고 "무엇이 돌았지"를 되묻는
   상황이 없어야 한다.
3. **`gate_filter` 는 단조성을 검사한다** (`assert_monotone`). 이분탐색의 전제이고,
   설정으로 임의 지표를 넣을 수 있게 된 이상 보장이 필요하다. 같은 이유로
   `gate_filter` 에는 `expr` 을 금지한다 — 임의 식의 단조성은 보장할 수 없다.
4. **결측은 위반이 아니다.** 모르는 것을 위반으로 단정하면 데이터 결측이 곧 배제가 된다.
5. **금융업 제외는 선택이 아니다.** 은행은 예금이 부채다. 부채·수익성 계열 체크에
   `exclude_sectors` 가 비어 있으면 테스트가 실패한다.

#### 게재 축 — tier 와 분리한다 (2026-08-07)

검증을 통과한 밸류 트랩이 다이제스트 본문에 대문짝만하게 실리는 것을 막아야 한다.
그런데 **재무 위험을 `tier` 에 섞으면 안 된다** — tier 는 '테마 배정이 검증됐는가'
한 축이고, 거기에 재무 품질을 얹으면 tier A 정밀도가 분류 품질을 재지 못하게 된다.
`A+B = 검증실패 0건` 항등식도 무너진다. 그래서 축을 하나 더 둔다.

```
tier          테마 배정이 검증됐는가        (A/B/C/reject)
risk_groups   재무 위험이 몇 범주에 걸치는가  (0,1,2,…)
```

본문 게재 = `tier == A` **그리고** `risk_groups < max_risk_groups_for_body`(기본 2).
걸러진 종목은 바로 아래 "재무 경고로 본문 보류" 절에 이유와 함께 실린다 — 감추지 않는다.

**개수가 아니라 범주 수를 센다.** `low_roic` 과 `low_roe` 는 같은 약점을 두 번
말하는 것이라 개수로 세면 한 가지가 둘로 계산된다. 체크마다 `risk_group` 을
선언하게 하고(`polarity: risk` 면 필수), 켜진 범주의 개수를 센다.

| polarity | 뜻 | 예 |
|---|---|---|
| `risk` | 재무 위험. `risk_group` 필수 | low_roic·cfo_shortfall·high_leverage |
| `positive` | 가산 신호 | high_dividend·treasury_heavy |
| `neutral` | 중립 또는 데이터 품질 | no_dividend·dividend_data_inconsistent |

범주: 수익성 / 현금창출 / 재무구조 / 배당지속 / 지배구조.

실측(tier A 14종목): 0범주 7 · 1범주 5 · 2범주 2. 보류된 2종목은
**화천기공**(현금창출+수익성)과 **성신양회**(수익성+재무구조)다. 둘 다 PER 5~7 인데
싸 보이는 이유가 재무에 있다.

회귀 테스트가 `assign_tier`·`hard_flag_count` 소스에 재무 체크 이름이 새어들지
않았는지 검사한다 — 축이 다시 섞이는 것을 코드 수준에서 막는다.

#### LLM 에는 넘기지 않는다

이 체크들은 **투자 퀄리티** 신호이지 데이터 품질 신호가 아니다. `METRIC_KEYS` 에서
밸류에이션을 뺀 것과 같은 이유로 evidence pack 에 넣지 않는다 — LLM 의 임무는
사업 분류이고, "이 회사는 ROIC 가 낮다"는 정보는 그 임무를 흐린다.
대신 다이제스트 tier A 표에 **리스크 열**로 실린다.

```
| 종목 | PER | PBR | FCFY | 리스크 | 논거 |
| 000850 화천기공 | 5.0 | 0.21 | 7.9% | cfo_shortfall, low_roic, low_roe | ... |
| 210540 디와이파워 | 4.8 | 0.39 | 21.9% | - | ... |
```

같은 PER 5배라도 왜 싼지가 갈린다.

### 적응형 게이트 — LLM 진입 종목 수 통제

정량 필터를 `tightness` 스칼라 `t ∈ [0,1]` 로 loose↔tight 사이에서 보간하고,
통과 종목 수가 목표에 수렴하는 `t*`를 이분탐색으로 찾는다. 각 필터가 `t`에 단조여야
`count(t)`도 단조가 되어 이분탐색이 성립한다.

```yaml
filters:
  - {metric: per, direction: lower_better, loose: 15.0, tight: 6.0, exclusive_zero: true}
  - {metric: pbr, direction: lower_better, loose: 1.20, tight: 0.55, exclusive_zero: true}
gate:
  mode: target_count        # fixed | target_count | rank_top_n
  target_count: 60
  hard_cap: 100
  hysteresis: 0.08
  budget: {enabled: false, max_input_tokens: 600_000, est_tokens_per_stock: 8_000}
```

- **`budget.enabled`** 로 목표 개수를 토큰 예산에서 역산할 수 있다 (240k / 8k → 30종목).
- **히스테리시스**: 직전 편입 종목은 `t* − hysteresis`(더 느슨한 값)에서 재평가한다.
  임계값이 매 실행 떠다니면 바스켓이 비경제적 이유로 회전한다.
- **`resolved_thresholds` 를 런 매니페스트에 기록한다.** 기록하지 않으면 그 실행은 재현 불가.
- 수렴 실패 시 `converged: false` 를 정직하게 남긴다 (조용히 근사치를 쓰지 않는다).

산출: `screens/{run_date}/survivors.parquet` + 통과/탈락 사유 로그(`why_excluded`).
**탈락 사유 로그는 반드시 남긴다** — "왜 이 종목이 안 나왔나"를 못 답하면 신뢰가 무너진다.

## 5. L4 — 엔리치먼트 (LLM 입력 준비)

생존 종목당 하나의 **evidence pack**을 만든다. 이게 LLM이 볼 수 있는 세계의 전부다.

```
enrich/{run_date}/{ticker}/
  business.md        # 사업보고서 "II. 사업의 내용" 원문 발췌 (KR) / DescriptionOfBusinessTextBlock (JP)
  segments.json      # 세그먼트별 매출·영업이익·비중
  disclosures.json   # 최근 180일 공시 제목 + 접수일 (본문 아님)
  metrics.json       # L2 지표 + quality_flags
  meta.json          # doc_ids, 원문 URL, 추출 시각, 텍스트 sha256
```

- **본문은 잘라내되 원문 그대로**: 요약을 미리 하면 인용 검증(§7 V1)이 불가능해진다.
  길이 초과 시엔 요약이 아니라 **섹션 단위 발췌**로 자른다. 무엇을 버렸는지 `meta.json`에 기록.

**사업보고서 원문 파싱 (`ingest/dart_document.py`) — 실전 함정 두 개**

1. **제출 zip 안에는 본문 + 첨부가 함께 들어 있다.** 삼성전자 FY2024 제출물은
   `20250311001085.xml`(6.3MB, 본문), `..._00760.xml`, `..._00761.xml`(감사보고서).
   이름순 첫 파일을 집으면 **감사보고서를 사업보고서로 착각한다**(실제로 그랬다).
   본문은 `{rcept_no}.xml`, 없으면 최대 크기 파일.
2. **태그를 이름만 보고 자르면 속성이 본문에 샌다.** `</?P[ >]` 는 `<P USERMARK="F-16 B">`
   에서 `<P ` 만 먹고 `USERMARK="F-16 B">` 를 본문에 남긴다. LLM 이 그걸 사업 설명으로
   읽고 V1 인용 검증까지 오염된다. 여는 꺾쇠부터 닫는 꺾쇠까지 통째로 소비하되,
   따옴표 안의 `>` 를 종료로 오인하지 않아야 한다.

사업보고서 접수번호는 별도 조회 없이 **`facts_financial.source_doc_id`(FY 재무 fact)를
재사용**한다 — 같은 제출물이므로 API 호출이 절약된다.
- 뉴스는 초기 스코프에서 제외 권장. 저작권·품질·PIT 정합성(기사 시각) 리스크가 크고,
  공시 제목만으로도 테마 신호는 상당 부분 나온다. 필요해지면 공시 제목 → 뉴스 순으로 확장.
- 세그먼트 비중은 **숫자로** 뽑아둔다. §7 V3 검증의 입력이 된다.

## 6. L5/L6 — LLM 테마 태깅 & 클러스터링

### 6.1 왜 2단계인가

한 번의 콜에 60종목을 넣고 "테마로 묶어줘"는 하면 안 된다:
- 순서 의존성(앞쪽 종목이 테마를 선점), 후반부 종목 누락, 재현 불가, 캐시 불가, 실패 시 전체 재시도.

→ **map(per-stock 태깅, 병렬·캐시 가능) → reduce(테마 사전 정규화·병합)**

### 6.2 테마 사전 (taxonomy) — 드리프트 방어

`configs/themes/taxonomy_v1.yaml`에 고정 테마 30~40개를 정의(id, 한글명, 정의문, 대표 키워드, 허용 섹터 집합).
LLM은 **이 사전에서만 고를 수 있다.** 다만 `proposed_new_theme` 필드를 열어두고,
새 테마는 사람이 승인해야 다음 버전 사전에 편입된다(taxonomy는 semver로 버전 관리).

> 이유: free-form 테마명은 실행할 때마다 바뀌어서 **테마별 시계열 성과 추적이 불가능**해진다.
> 사전 고정이 곧 측정 가능성이다.

### 6.3 L5 — per-stock 태깅 (구조화 출력)

- 모델: `claude-sonnet-5` (판단), 문서 발췌·세그먼트 정형화 같은 기계적 단계는 `claude-haiku-4-5`
- **자유 텍스트 금지 — tool use 스키마로 강제**

```jsonc
{
  "ticker": "005930",
  "assignments": [
    {
      "theme_id": "ai_power_infra",
      "role": "core",                    // core | adjacent | peripheral
      "rationale": "한 문장, 40자 이내",
      "evidence": [
        {
          "source": "business.md",
          "quote": "원문에서 그대로 복사한 문장",   // ← 검증 대상
          "char_offset_hint": 10432
        }
      ],
      "revenue_share_claim": 0.35,       // LLM이 주장하는 해당 사업 매출 비중
      "confidence": 0.82
    }
  ],
  "proposed_new_theme": null,
  "abstain": false,                      // 근거 불충분 시 true — 이걸 허용해야 환각이 준다
  "input_hash": "sha256:…",
  "prompt_version": "tag@v3",
  "model": "claude-sonnet-5"
}
```

프롬프트 핵심 규칙:
1. "evidence.quote는 제공된 문서에서 **문자 그대로** 복사할 것. 바꿔쓰기 금지."
2. "근거를 찾을 수 없으면 `abstain: true`. 추측 금지."
3. "최대 3개 테마. 억지로 채우지 말 것."
4. "주가·투자매력도·목표주가 언급 금지. 사업 내용만 판단."

**캐시 키** = `sha256(model + prompt_version + taxonomy_version + evidence_pack_hash)`
→ 동일 입력 재호출 비용 0, 재현성 100%. `llm/tags/{cache_key}.json`.

### 6.4 L6 — 클러스터 리듀스

전 종목 태그를 모아서:
- 같은 테마 id로 그룹핑(결정론적, LLM 불필요)
- 멤버 1개뿐인 테마 → 인접 테마 병합 후보로 LLM에 1콜(제안만, 자동 적용 X)
- 테마별 요약 한 문단 생성(멤버 rationale만 입력, 원문 재입력 X → 토큰 절약)

### 6.5 비용 추정

생존 60종목 × (발췌 정형화 1콜 + 태깅 1콜) + 리듀스 몇 콜.
evidence pack 평균 8k 토큰 가정 시 주간 실행 기준 월 수 달러 수준. 캐시 히트 시 더 낮음.

## 7. L7 — 검증 레이어 ★ (이 파이프라인의 정체성)

> ⚠ **이 절의 등급(A/B/C) 체계는 폐지됐다.** 현재는 `verified` / `rejected`
> 두 상태와 `share_evidence` 여섯 값을 쓴다. 아래 V1~V3 의 *동작*은 대체로
> 유효하나 *등급 판정* 부분은 [`ARCHITECTURE.md` §5](ARCHITECTURE.md#5-l7-검증--이-파이프라인의-정체성)를 볼 것.

LLM 출력은 검증을 통과하기 전엔 **후보(candidate)**일 뿐이다.

### V1. 인용 근거 검증 (citation grounding) — 가장 싸고 가장 강력

`evidence.quote`가 evidence pack 원문에 실제로 존재하는가?
- 1차: 정규화(공백/전각·반각/조사 제거) 후 exact substring match
- 2차: 실패 시 `rapidfuzz.partial_ratio ≥ 92` 로 fuzzy match
- 실패 → **해당 assignment 폐기**(reject), `hallucinated_citation` 카운트 증가

> 이 하나만으로 환각성 테마 배정의 대부분이 제거된다. LLM 호출 없이 순수 코드로 돌아간다.

### V2. 섹터 정합성 대조

`configs/themes/theme_sector_matrix.yaml`에 테마 ↔ 허용 섹터(KRX 업종 / TSE 33업종) 매트릭스를 사전 정의.
- 테마의 허용 섹터 집합에 종목 섹터가 없으면 → `sector_conflict` 플래그
- **reject가 아니라 flag**: 신규 사업 진출은 실제로 존재한다(예: 화학사의 2차전지 소재 전환).
  대신 conflict 시 **evidence를 2개 이상 요구**하고, 미충족이면 강등.

### V3. 세그먼트 매출 비중 검증 — 테마 편승 차단

LLM의 `revenue_share_claim`을 `segments.json`의 실제 숫자와 대조:
- 실제 비중 ≥ 20% → `role: core` 허용
- 5~20% → `adjacent`로 강등
- < 5% 또는 세그먼트에 흔적 없음 → `peripheral` 강등 + `theme_riding_suspect` 플래그
- LLM 주장치와 실제치 괴리 > 0.2 → `share_overclaim` 플래그

> "AI 테마"라며 매출 2%짜리 신사업을 근거로 붙는 케이스가 가장 흔한 오탐이다. 여기서 잡는다.

### V4. 자기일관성 / 교차검증 (선택적, 저신뢰 케이스만)

`confidence < 0.7` 또는 V2/V3 플래그가 붙은 건에 한해:
- 프롬프트 변형판으로 재실행(순서 셔플, 테마 후보 제시 순서 변경) → 배정 불일치 시 `unstable` 플래그
- 비용이 허용되면 다른 모델로 2차 판정
- 전건에 돌리지 않는다. 비용 대비 효용이 급감한다.

#### 라벨링 규칙 명문화 + 전건 재검수 (v2)

v1 은 단일 검수였고, 라벨 1건(토비스)의 오류가 오분류율을 5.9%→2.9% 로 움직였다.
규칙이 없으면 지표가 "데이터가 얼마나 정확한가"가 아니라 "그날 라벨러가 어떻게
느꼈나"를 잰다. `tests/golden/LABELING.md` 에 규칙 6개를 못박고 62종목을 재검수했다.

두 가지 장치로 라벨 1건의 지렛대를 줄였다:

1. **분모 확대.** core 보유 44 → 60. 사전 공백을 메운 부수 효과다.
2. **`confidence: certain | contested`.** 판정이 갈릴 수 있는 라벨 10건을 표시하고
   **사유를 필수로** 적게 했다(테스트가 강제). 지표에서 빼지 않되 certain-only 를
   함께 보고해, 숫자가 그 판단에 얼마나 기대는지 드러낸다.

갈리는 유형은 대체로 셋이다 — 테마 경계가 겹치거나(토비스: 차량용 디스플레이가
전장인가 디스플레이 부품인가), 사전이 그 업종을 상정하지 않았거나(TYM 농기계,
동양이엔피 SMPS, 유나이티드·테라젠이텍스 완제 제약), 세그먼트가 쪼개져 있지 않아
수치로 가를 수 없거나(디바이스: 반도체 FOUP 과 OLED 마스크 세정이 한 부문).

**tier A 건수는 세그먼트 커버리지가 그대로 결정한다.** 등급 기준의 문제가 아니라
입력 데이터의 문제라는 것이 실측으로 확인됐다 — 입증 커버리지를 13%→23%→32% 로
올리자 tier A 가 2→6→9 건으로 따라 올라갔다(정밀도는 100% 유지).

CI 회귀 게이트: `tests/test_m2_golden.py` — A+B 오분류율 ≤5%, 재현율 ≥65%,
**A+B 정밀도가 검증 전보다 높지 않으면 실패**(검증이 값을 못 하면 게이트가 막는다),
재현율이 검증 전 대비 5%p 넘게 깎여도 실패. 추가로 `A+B == 검증실패 0건`이
성립하는지 검사한다 — 등급이 플래그 신호와 어긋나면 등급이 거짓말을 하는 것이다.

#### 이 측정으로 잡아낸 실제 결함 7건

1. **V1 퍼지 매칭이 한 번도 돌지 않았다.** `rapidfuzz` 미설치 시 `verify_citation`
   이 조용히 `False` 를 반환 → 완전일치만 남아 환각률이 부풀려졌다.
   (`apply_hard_guards` 의 silent skip 과 같은 부류.) 이제 `RuntimeError` 를 던지고
   `requirements.txt` 에 필수 의존성으로 선언. **환각률 5.1% → 1.7%.**
2. **V3 가 "비중 미기재"를 "비중 0%"로 읽었다.** LLM 이 `revenue_share_claim` 을
   채우지 않은 6건을 하한 미달로 강등 → 검증이 아니라 메타데이터 누락 처벌이었다.
   `0.0 < claim < floor` 일 때만 강등하도록 수정. **재현율 59.1% → 73.3%.**
3. **등급 정의가 검증 실패 1건을 무료 통과시켰다.** `n_hard <= 1 → B`. 그 결과
   V2 가 정확히 짚어낸 오탐이 B 에 살아남아 검증의 정밀도 기여가 0 이었다.
   실패는 1건부터 C. 아래 "등급 정의" 참조. **A+B 정밀도 97.1% → 100%.**
4. **`allowed_sectors` 공백으로 정상 배정이 섹터 충돌로 찍혔다.** 와이어하네스·
   커넥터 업체(티에이치엔·한국단자공업)는 KSIC 28 전기장비(`ELEC_EQUIP`)로
   분류되는데 `auto_parts` 가 이를 허용하지 않았다. 시멘트사의 폐기물 처리 겸영
   (`NONMETAL_MIN` → `recycling_environment`)도 같은 문제. 두 코드 추가.
   **재현율 66.7% → 73.3%** (섹터 충돌로 C 에 떨어졌던 정답 3건 복구).

   > ⚠️ 이 두 수정은 골든셋 결과를 **본 뒤에** 한 것이라 테스트셋 적합 위험이 있다.
   > 완화책은 근거를 KSIC 분류 구조와 업계 관행에 두어 골든셋과 독립적으로
   > 검증 가능하게 한 것뿐이다. 재현율 6.6%p 개선치는 낙관 편향으로 읽어야 한다.
5. **태그 캐시가 프롬프트 변경에 무효화되지 않았다.** 캐시 키가
   `taxonomy['version']` — **사람이 손으로 올리는 문자열**에 걸려 있었다.
   테마 정의를 고치고 버전을 안 올리면 재실행이 조용히 옛 결과를 돌려준다.
   실제로 `shipping_freight` 제외 조항을 추가하고 재실행했는데 62종목 결과가
   **한 건도 바뀌지 않았다.** 이제 시스템 프롬프트의 실제 내용을 해시한다
   (`system_fingerprint`). 회귀 테스트로 고정.
6. **`max_tokens=2048` 로 응답이 절단됐다.** 인용을 요약 없이 원문 복사하게 하는
   설계라 출력이 길다. 게다가 `_parse` 의 `next()` 가 텍스트 블록 부재 시
   `StopIteration` 을 던져, 코루틴 안에서 `coroutine raised StopIteration` 이라는
   원인 불명 에러가 됐다. `stop_reason` 을 담은 명시적 예외 + 4096 으로 수정.
7. **`shipping_freight` 가 포워딩을 상정하지 않았다.** CJ대한통운이 "선박을 이용하여
   컨테이너 및 Bulk 화물을 운송" 이라는 포워딩 서술로 **tier A** 오탐이 됐다.
   포워더는 운임 상승 시 선사와 손익 방향이 반대(매입원가 상승)라 같은 사이클로
   볼 수 없다. inclusion 이 전부 선사·터미널 활동인데 exclusion 이 그 의도를
   말하지 않았을 뿐이라, 제외 조항을 명시했다.

보이는 게 가장 위험하다. 원인은 서로 다른 3개의 버그였다.

|---|---|---|
| 033270 유나이티드 | 외부감사에 관한 사항 | 상호참조를 섹션 시작으로 오인 |

1. **후보 선정이 '가장 긴 것'이었다.** 목차 항목을 피하려 넣은 규칙인데,

   우선순위 소제목이 0개로 보였고, 예산이 잡동사니로 채워졌다.

   넘자 탈락하고 그 자리를 '원재료 및 생산설비'가 채웠다(코메론·제이에스코퍼레이션).
   잘린 개요가 온전한 원재료 명세보다 낫다 — 잘라 넣도록 수정.

추가로 **출력 순서를 원문 순서로** 되돌렸다. 예산을 우선순위로 채운 뒤 그 순서
그대로 이어붙이면 매출표가 사업 설명보다 앞에 오는 뒤죽박죽 문서가 LLM 에 들어간다.

회귀 가드: `tests/test_m2_document.py` — 캐시된 사업보고서 **전건**에서 발췌
앞부분에 '사업의 개요'가 있어야 한다. 도입 시점에 4건을 잡았고 지금은 62/62 통과.

#### 세그먼트 확장 (2026-08-07)

V3 가 쓸 수 있는 수치를 늘리는 작업. **커버리지 29%→66%, 입증됨 13%→32%.**
입증된 20건은 전건 수동 감사로 정확함을 확인했다(코메론 줄자 94%, HDC현대EP
PO 66%/PS 31% 등 골든셋과 일치). 그 결과 **tier A 가 2→9 건**으로 늘었다.

가장 큰 원인은 DART 매출실적표가 거의 전부 **rowspan 표**라는 것이었다.
사업부문 셀이 rowspan 으로 묶이면 이어지는 행에는 그 셀이 **빈 셀이 아니라 아예
없다.** 왼쪽 기준 열 정렬이 성립하지 않아 `내수`·`수출` 이 사업부문으로 읽혔다.

```
['타이어','제품','타이어','한국', 460299, 406691, 408017]   ← 그룹 시작
['해외', 4048566, ...]                                     ← rowspan 연속행
['합계', 4508865, ...]                                     ← 그룹 소계 = 이 부문 매출
```

숫자를 **오른쪽 끝에서부터** 잡고 소계 행으로 그룹을 닫도록 재작성했다. 그 과정에서
드러난 것들:

- **표 첫 행이 헤더가 아니다.** DART 는 `(단위 : 백만원)` 을 별도 행으로 먼저 넣는다.
  첫 행만 보고 열 이름을 찾다가 정상 매출실적표를 통째로 버리고 있었다
  (팜스토리·넥센타이어·KG스틸 전부 이 이유로 0건).
- **총합계를 그룹 소계로 오인**하면 마지막 부문에 회사 전체 매출이 들어간다
  (성신양회 기타 1.6%→100%). 총합계를 만나면 표를 끝낸다 — 평문화 과정에서
  다음 표가 같은 블록에 붙는 일이 흔하다.
- **한 그룹에 소계가 여러 번** 나오면 첫 소계만 쓴다. 덮어쓰면 마지막 작은 소계가
  부문 매출로 남는다(코메론 줄자 664억→14억).

**틀린 세그먼트는 없는 것보다 나쁘다** — V3 가 그 수치로 정상 배정을 강등한다.
그래서 퇴화 파싱을 명시적으로 거부한다(`_is_degenerate`): 같은 그룹명 반복
(= 행 묶기 실패), 지역·법인·매출유형이 **세그먼테이션 축**인 경우,
하나가 99.9% 이고 나머지가 0 인 집계 실패, 단일인데 이름이 잡음인 경우.

거부 규칙은 과하면 쓸 수 있는 수치까지 잃는다. 두 번 조정했다:

- **`상품`·`제품` 같은 이름이 들어 있다는 이유만으로 표를 버리면 안 된다.**
  '전력기기 65% / 상품 11% / 신재생 24%'(피에스텍)는 정상 파싱이다.
  그런 이름의 **합이 40% 이상**일 때만 세그먼테이션 축으로 보고 거부한다.
- **단일 사업부문 회사는 실재한다.** '99.5% 이상이면 집계 실패'로 잡으면
  디바이스(오염제어 99.7%)·우원개발(토공 99.8%)이 함께 죽는다.

#### 단일 사업부문을 인정한 것이 tier A 를 크게 늘렸다

`MIN_SEGMENTS=2` 때문에 사업부문이 하나인 회사는 통째로 버려지고 있었다.
그런데 V3 에게는 그게 **가장 쓸모 있는 정보**다 — "이 회사는 사실상 100% 이 사업"이면
core 배정을 그대로 확인해준다. 다만 '접기가 실패해 하나로 뭉친 것'과 구별할 수단이
매출 대조뿐이라, **대조를 통과할 때만** 인정한다.
한섬·SK가스·바텍·동양이엔피·디와이파워·키스트론 등이 이렇게 살아났다.

서술문 쪽은 반대다. 서술문은 항상 `corroborated=True` 라 단일 추출을 걸러낼 근거가
없고, 실제로 문장 하나에서 % 하나만 잡히면 대개 오독이다(한전 '기타' 100%,
폴라리스AI파마 '내수와 수출' 100%). 서술문 단일은 무조건 버린다.

#### 문맥 배제 — 매출 대조는 생각보다 약하다

생산실적표는 단위가 톤·대라 금액이 아닌데, 배율 후보(1e3/1e6/1e8) 중 하나가
매출과 우연히 맞을 수 있다. 팜스토리의 사료 **1,598,668톤** × 1e6 이 매출 1.45조와
10% 차이로 대조를 통과해, 사료 99%/육가공 0% 라는 틀린 값이 입증됨으로 올라왔다.
`생산실적·생산능력·가동률·원재료·매입실적` 을 부정 문맥에 추가했다.

같은 이유로 순위에서 **문맥이 방법 신뢰도보다 앞선다.** 넥센타이어에서는 깨진
'주요 제품 등의 현황' 표가 대조를 통과해, 정확한 '매출실적' 표를 이겼다.
어느 절 아래에 있는 표인가가 그 표가 무엇인지를 훨씬 잘 말해준다.

매출 대조에 실패한 표는 **매출실적 절 아래에 있을 때만** 남기고
`table_amount_unverified` (corroborated=False) 로 표시한다. 매출실적표에는
`(내부거래포함)` 처럼 연결매출과 정의가 다른 것이 흔해 곧바로 버리면 과잉 차단이지만,
아무 표에나 허용하면 단가표가 다시 들어온다 — 매출 대조는 그걸 막으려고 넣은 검사다.

#### 드러난 택소노미 공백

골든셋 62종목 중 18종목은 **어떤 테마에도 core 로 넣을 수 없다.** LLM 의 기권(37%)
상당수는 오류가 아니라 사전에 칸이 없어서다: 육상물류·택배(CJ대한통운),
LPG 유통(E1·SK가스), 전자결제(KG이니시스·KG파이낸셜), 의료기기(바텍),
디스플레이 장비·부품(HB테크놀러지·동아엘텍·뉴프렉스·비에이치·제이엠티),
렌탈(AJ네트웍스), 광고대행(HS애드·이노션 — 명시적 제외).

- 남은 항목: 사람 검수, JP 40종목, per-theme 최소 표본 확보(현재 테마당 1~5건)

### 종합 등급

두 축이 **서로 다른 것**을 뜻한다. 이걸 한 축으로 뭉개면 등급이 거짓말을 한다.

| | 뜻 | 가르는 것 |
|---|---|---|
| A vs B | 확인됐는가 / 확인할 수 없었는가 | 근거 데이터의 **유무** |
| B vs C | 어긋난 데가 있는가 | 검증의 **성패** |

```
tier A : V1 pass ∧ 검증실패 0건 ∧ 확인불가 0건 ∧ role=core ∧ confidence ≥ 0.75
tier B : V1 pass ∧ 검증실패 0건          (확인 불가 항목은 있어도 됨)
tier C : 검증실패 ≥ 1건
reject : V1 fail ∨ 사전에 없는 테마
```

**검증 실패(hard)** — 대조할 수치가 있었는데 어긋났다:
`role_downgraded_by_actual`, `share_overclaim`, `segment_not_found`,
그리고 `sector_conflict`는 **role=core 일 때만**.

> `sector_conflict` 가 role 조건부인 이유: 섹터는 회사당 하나만 부여되므로
> adjacent/peripheral 테마가 종목 섹터와 어긋나는 건 설계상 정상이다
> (건설사의 peripheral `nuclear_smr` 등). 실측 17건 중 13건이 비-core 였다.

**확인 불가(unverifiable)** — 대조할 근거가 없었다. A 만 막고 C 로 내리지 않는다:
`segment_data_unavailable`, `segment_data_unverified`, `segment_name_missing`,
`sector_unknown`, `core_without_share_evidence`.

> `core_without_share_evidence` 가 실패가 아닌 이유: 골든셋 실측에서 이 플래그가
> 붙은 5건이 **전부 정답**이었다. 판별력 0 인 신호를 실패로 세면 잡음만 늘어난다.
> 비중을 '말하지 않은 것'은 배정이 틀렸다는 증거가 아니다.

이전 정의(`검증실패 ≤ 1건 → B`)는 실패 1건을 무료 통과시켰고, 그 틈으로
V2 가 정확히 짚어낸 오탐이 B 에 살아남아 **검증의 정밀도 기여가 0** 이었다.

다이제스트 본문은 **A만**. B는 접힌 섹션. C/reject는 별도 감사 로그.

산출: `verify/{run_date}/verdicts.parquet` + `verify/{run_date}/metrics.json`
(오분류율, 인용실패율, 강등율, tier 분포 — **매 실행 기록해 시계열로 관리**)

## 9.4 스캔 주기와 리밸런스 주기 ✅ 2026-08-08

```
스캔(일별)      가격 → 지표 → 게이트 → **진입·이탈 후보만 보고**. 바스켓 불변.
리밸런스(주/월)  바스켓 확정 → enrich → tag → verify → golden
```

**히스테리시스 기준은 '직전 실행'이 아니라 '직전 리밸런스'다.** 전자를 쓰면
일별 운영에서 기준이 매일 어제로 밀린다 — 어제 편입된 종목이 오늘도 느슨하게
평가되고 그게 매일 이어져 **바스켓이 서서히 표류한다.** 임계값 근처 종목의 잦은
교체를 막으려던 장치가 정반대로 작동하는 셈이다.

`screens/_basket.json` 이 확정 바스켓을 담고, **`--rebalance` 에서만 갱신된다**:

```json
{"rebalanced_at": "2026-08-06", "members": [...62개...], "config_version": 2}
```

스캔은 표류를 매니페스트와 화면에 남긴다:

```
스캔: 확정 바스켓 62종목 (2026-08-06, 1일 전) 대비 진입후보 2 이탈후보 0 — 바스켓은 그대로
  진입후보 ['003010', '052900']
  → 확정하려면 `screen --rebalance` (그 뒤 enrich/tag/verify/golden)
```

바스켓이 없으면 "히스테리시스가 적용되지 않았다"고 명시한다 — 조용히 넘어가면
장치가 꺼져 있는 줄 모른다. 구버전 `_last_members.json`(티커 배열)도 읽지만
리밸런스 시점을 모르므로 '확정된 적 없음'으로 취급한다.

### 골든셋 코호트 가드

**라벨은 티커 단위다.** 리밸런스로 바스켓이 바뀐 뒤 측정하면 오분류율이
'데이터 품질'이 아니라 '오늘의 종목 구성'을 잰다. `golden` 이 겹침을 먼저 보고하고,
80% 미만이면 **중단한다**(exit 1):

```
코호트: 라벨 62 / 측정 대상 62 / 겹침 62 (100%)
```

```
중단: 코호트 겹침 50% < 80%. 바스켓이 바뀐 뒤 라벨을 갱신하지 않은 상태로 보인다
      — 지금 내는 숫자는 데이터 품질이 아니라 종목 구성을 잰다.
```

감수하려면 `--allow-cohort-drift` 로 **명시적으로** 감수한다. 조용히 숫자를 내면
그 숫자를 신뢰하게 되므로 막는 쪽을 택했다.

## 9.5 일별 운영

```
scripts/daily_prices.py     # 시세 갱신 (+ --derive)
scripts/daily_prices.ps1    # Windows 작업 스케줄러 래퍼, 매일 16:10
```

**as_of 는 오늘이 아니라 마지막 거래일이다.** `build_price_table` 이
`df["date"] = as_of` 로 저장하므로, 토요일에 오늘 날짜로 돌리면 금요일 종가가
토요일 행으로 들어간다 — 휴장일 유령 행이 생기고 수익률 계산이 깨진다.

거래일은 **공휴일 달력 대신 프로브로 정한다.** 삼성전자를 12일치 조회해
데이터가 실제로 존재하는 마지막 날짜를 쓴다. 달력은 매년 갱신해야 하고
임시휴장을 못 잡는다. 요일 조건을 스케줄러에도 두지 않는 이유가 같다 —
판정이 두 군데 있으면 임시휴장 때 어긋난다.

**부분 적재를 완료로 오인하지 않는다.** 행이 있다는 것과 다 받았다는 것은
다르다. 커버리지가 90% 미만이면 다시 받고, 수집 후에도 90% 미만이면
**비정상 종료**한다 — 조용히 성공으로 끝내면 스케줄러가 실패를 기록하지 못한다.

실측: 2,678종목 **319초**(workers=16). DART 호출 **0회**(주식수는
`{corp}_{year}_{reprt}` 로 캐시되어 2,599건이 이미 있다). LLM 비용 **0원**
(`pack_hash` 가 주가와 독립 — METRIC_KEYS 가 2,597/2,598 동일함을 실측 확인).

인코딩은 **양쪽 다** 설정해야 한다. `PYTHONIOENCODING` 만 두면 PowerShell 이
UTF-8 바이트를 cp949 로 오독해 로그 파일에 깨진 글자가 남는다(실측).

### 백테스트를 위한 축적은 하지 않는다

한때 "일별 축적을 시작하면 백테스트 자산이 쌓인다"고 적었으나 **취소한다.**
검증해보니:

- `screens/{date}/survivors.parquet` 이 이미 의사결정 입력을 동결한다
  (close·shares_common·market_cap_used·per·pbr·fcf_yield·adtv_20d).
  "그날 왜 이 62종목이 나왔나"는 축적 없이 재현된다.
- FDR 이 임의 과거 구간을 준다(2020년·2024년 정상 조회). 애초에 지금도
  매번 20일 창을 받아 19일치를 버리고 있다.
- 오히려 **소스가 수정주가를 준다면 매일 저장하는 쪽이 더 나쁘다** —
  분할 전 행은 옛 기준, 분할 후 행은 새 기준으로 남아 시계열에 불연속이 생긴다.
  온디맨드 조회는 최소한 일관된 기준을 준다.

축적이 사는 것은 **소스가 과거를 바꾸거나 잃을 때의 보험**뿐이다. 쌓이는 것은
부작용이지 목적이 아니다(2,598행/일 × 250일 ≈ 65만행, 수십 MB — 해롭지도 않다).

## 11. 열린 결정 사항

1. **실행 주기**: 주간 vs 월간. 딥밸류 스크린은 회전율이 낮아 월간으로 충분할 수 있음 → LLM 비용도 1/4.
2. **`available_at` lag**: 0영업일 vs 1영업일. 백테스트 보수성 vs 실전 신속성.
3. **뉴스 포함 여부**: 초기 제외 권장(§5).
4. **금융업 트랙**: 완전 제외 vs 별도 스크린(PBR·ROE 기반). 초기엔 제외가 단순.
5. **taxonomy 초기 테마 목록**: 이건 도메인 판단 — 30개 초안을 먼저 잡아야 M2 착수 가능.
